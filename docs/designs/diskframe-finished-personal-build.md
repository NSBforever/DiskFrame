## Problem Statement
DiskFrame is a personal Windows tool for browsing photos and videos straight off drives, without importing them into a library. The ask was "complete it end to end with no bugs". In this session "complete" was narrowed to the three jobs the owner relies on: browse big drives fast, view photos and play videos, and find things. Those must work on the three drive types used: an external USB HDD/SSD that may be asleep, SD cards and phone dumps, and internal C:/D: folders.

The failures actually hit are:
- blank or slow thumbnails;
- videos that won't play right;
- freezes, lag and crashes.

Search works today and is not a pain.

A performance pass earlier the same day already removed the measured causes of scroll lag and main-thread stalls:
- fast-scroll input latency p50 went from 188 ms to 67 ms;
- time from opening a drive to a screen of thumbnails went from 11.1 s to 3.3 s on a quiet machine;
- main-process stalls under load went from 39 s to 3.6 s.

What remains sits on the formats a phone produces: iPhone HEIC photos and 4K HEVC video.

## What Makes This Cool
Plug in a phone dump and it just works, the way the phone's own gallery does: every tile has a picture, and every clip plays the instant it's opened, HDR and all. Nothing is imported, converted or copied. And "no bugs" stops being a hope: it becomes a command the owner runs before installing a build, which says PASS or FAIL for each drive.

## Constraints
- **Machine:** one Windows 11 laptop with a Ryzen 7 5800H, Radeon integrated GPU and 16 GB RAM. Only this machine has to work.
- **Disk space:** drive C: had about 3 GB free when measured. The thumbnail, HEIC and transcode caches must stay within their budgets and fail gracefully when the disk is full.
- **Content:** iPhone HEIC; iPhone 4K HEVC .MOV, some Main 10 HDR; Android H.264 .MP4; occasional audio-only .MP4; occasional ProRes.
- **Windows codecs:** the HEVC Video Extensions are not installed. Windows/WIC thumbnails therefore cannot decode HEIC or HEVC, and DiskFrame must decode them itself.
- **Safe mode:** safe mode disables GPU acceleration, which also turns off Chromium's HEVC decode. A non-GPU playback path has to stay.
- **Design:** keep the existing UI and design. Features the owner doesn't use (trash, move, vault, AI search) get safety checks only, no new work.
- **mpv:** `resources/bin/win/mpv.exe` is gitignored, so a build can silently ship without it.
- **Uncommitted work:** the working tree holds this session's uncommitted audit changes next to the owner's uncommitted Recycle Bin work. The sharp 0.35.5 security upgrade sits on branch `claude/pensive-visvesvaraya-ee9d61` (commit `42c254f`).

## Premises
1. **Scope.** "Complete" means the three jobs above, on the three drive types above. Unused features get safety checks only.
2. **Native-first video, through a fixed path** (revised after the second opinion). Chromium plays the owner's H.264 and 4K HEVC Main 10 HDR clips itself: first frame in 28-114 ms in a bare `<video>`, measured on this machine. But DiskFrame's own native path does not get there today:
   - `streamServer.ts` treats only `.mp4` + H.264 + 8-bit as native, and HEVC isn't in `isChromiumVideo`;
   - the `media:` handler (`index.ts:905`) calls `net.fetch` without forwarding the `Range` header;
   - so iPhone `.MOV` files fall back to a libx264 re-encode that loses HDR and seeks badly.

   The work is to fix that path. mpv then stays only for formats Chromium can't decode (ProRes, odd MKV/AVI/WMV) and for safe mode.
3. **"No bugs" is a test suite.** A fixed acceptance run, on real files and each drive type, decides done. It must be green before any build is installed.
4. **Ship an installed build.** The owner uses the app installed by `npm run build:win`, with ffmpeg and mpv verified inside it, not `npm run dev`.

## Cross-Model Perspective
Independent cold read by a fresh Claude subagent (Codex is not installed). Close paraphrase:
- **Coolest version:** one GPU pipeline for thumbnails, hover-scrub and playback, built on Chromium's own hardware HEVC decoder. A hidden window keeps long-lived `<video>` elements, seeks each clip and draws a frame to a canvas.
- **What the owner needs most:** the pains converge on HEVC. Every HEIC tile is a full 24 MP wasm decode for a 300 px tile, on a single worker (`heicPool.ts` `WORKERS = 1`; reviewer's estimate about 3.7 s each, not measured here). Meanwhile libheif-js exposes `_heif_image_handle_get_thumbnail`, which the worker never uses.
- **Challenged premise:** premise 2 as first written, which led to the revision above. The gate and the dropped `Range` header were verified against the code. That seeking breaks because of them is likely but unmeasured.
- **Reuse:** the bundled ffmpeg 6.1.1 already ships hardware decoders and `zscale`/`tonemap`. Immich's ffmpeg configuration is a reference worth copying from.
- **Weekend build:** HEIC embedded thumbnails first, then Range support, native-first playback and a video acceptance matrix.
- **Where this doc disagrees:** ffmpeg `-hwaccel` for thumbnails. `-hwaccel auto` measured 1.4-2.6 s per clip here against 0.8-1.3 s in software, because GPU init repeats in every ffmpeg process.

## Approaches Considered
- **A: Fix in place, behind an acceptance suite.** Chosen; see below.
- **B: One GPU media pipeline.** Not chosen: it adds the most new code exactly where "no bugs" was asked for, and is worth building only if the suite still shows video thumbnails as the bottleneck after A.
- **C: Generate thumbnails as soon as a drive is plugged in.** Not chosen: it moves the wait rather than removing it, and reads drives the owner didn't open.

## Recommended Approach
Approach A: fix the three slow paths where they are, prove each with a number, and gate installs on an acceptance suite.

- **HEIC tiles use the thumbnail already inside the file.** `heicWorker.ts` reads the primary image's embedded thumbnail through libheif's thumbnail API and cover-crops it to 300 px with sharp. It falls back to today's full decode when there is no thumbnail, or when its short side is below the size the tile needs (to be confirmed by the probe in Next Steps 1). The viewer's own full-size HEIC request must not wait behind a running thumbnail job.
- **The `media:` handler answers byte ranges.** It parses `Range` and returns 206 with `Content-Range`, `Accept-Ranges` and `Content-Length`. The existing path-safety and volume-identity checks run unchanged before any byte is served, and the range parser gets unit tests.
- **The viewer plays natively first.** `ImageLoader.tsx` tries a `<video>` on `media:` first. It hands over to the existing mpv path when the `<video>` errors, when no frame arrives within a short timeout, or when safe mode has turned off the GPU. The HEVC/10-bit exclusion in `streamServer.ts` goes, and HEVC no longer takes the libx264 re-encode.
- **An acceptance suite decides "done".** It builds on `scratch/perf` (`run.js` freeze and scroll metrics, `smoke.js` UI walk, `pintile.js`), plus two new checks:
  - a video matrix: first frame, seek to 90%, orientation, and which mode played it (native or mpv);
  - a cold-cache HEIC screen check: time until every visible tile shows a picture.

  It runs per drive type, from one command, against the installed build, and refuses to run against the real profile.
- **Builds are verified.** The build fails if `mpv.exe` or ffmpeg is missing from the packaged resources, and the suite runs against the installed exe.

## Open Questions
- Do the owner's iPhone HEICs carry an embedded thumbnail, and how big is it? If it is under about 300 px on its short side, the fast path needs a second tier: a decode of the HEVC tile grid at reduced size.
- Does `media:` answer 200 or 206 today, and does `video.seekable` cover the full duration of a large clip read from the USB HDD?
- Does Chromium's HDR-to-SDR rendering of an iPhone HLG/Dolby Vision clip on this laptop's SDR panel look right next to mpv's? This needs a side-by-side visual check.
- Which physical USB HDD and SD card will the suite run against? It needs the real devices, including the HDD asleep.
- Should the suite live in `scratch/perf` (untracked today) or be committed as `npm run accept`?

## Success Criteria
Each number is checked by the acceptance suite on each drive type unless marked as a manual check.
- **HEIC tiles:** a cold-cache screen of about 30 iPhone HEIC tiles shows a picture in every tile within 5 s from the internal SSD. The before number is measured first (Next Steps 1).
- **Video (internal SSD):** each matrix clip shows its first frame within 500 ms in the viewer; HEVC and H.264 play natively.
- **Video (USB HDD, awake):** each matrix clip shows its first frame within 1,500 ms.
- **Video (all clips):**
  - seeking to 90% shows a frame within 1 s;
  - portrait clips display upright;
  - ProRes plays through mpv;
  - the audio-only `.MP4` plays its audio, and its tile says "no preview".
- **Video (manual check):** an HDR clip does not look washed out next to mpv.
- **No freezes:** during the harness scenario, no main-process stall exceeds 250 ms. Opening a sleeping USB HDD never stalls the main process for more than 1 s, so Windows never shows "Not Responding".
- **One command:** the whole suite runs from one command and prints PASS or FAIL per check per drive. It is green against the installed build on all three drive types.
- **Baseline stays green:** `npm test`, typecheck and `npm run build` pass, with no new lint findings in touched files.

## Distribution Plan
- **Who gets it:** the owner's own machine, through the NSIS installer from `npm run build:win`.
- **Pipeline:** none. Builds are manual, and installing one is gated on the acceptance suite being green.
- **Binaries:** the build checks that `mpv.exe` and ffmpeg are inside the packaged `resources`, and fails if not. Where `mpv.exe` comes from must be documented, because it is gitignored.

3. **Range support in the `media:` handler**, with a unit-tested range parser.
4. **Native-first viewer.** Try `<video>` on `media:`, then mpv. Keep mpv for safe mode. Remove the HEVC/10-bit exclusion and the HEVC libx264 route.
5. **Acceptance suite:**
   - the video matrix, HEIC cold-screen check, harness freeze metrics and smoke walk;
   - tile size pinned before each run;
   - one wrapper command, run per drive type.
6. **Packaging check, installer build and full suite.** Add the mpv/ffmpeg packaging check, build the installer, install it, then run the suite on all three drive types.

## The Assignment
Build the fixture folder: copy 10 real files from your own SD card, phone dump or USB drive into one folder:
- an iPhone HEIC;
- an iPhone 4K HEVC `.MOV`, including one HDR clip;
